# 09. Архитектурные решения и альтернативы (ADR)

Документ фиксирует решения, действующие для базовой реализации. Решение можно пересмотреть только после воспроизводимого эксперимента или появления нового ограничения.

## ADR-001. Модульный монолит вместо микросервисов

**Статус:** принято.  
**Решение:** один Python application с изолированными пакетами `core`, `vision`, `reasoning`, `analysis`, `ui`.  
**Причина:** небольшой объём проекта; проще отлаживать frame → move pipeline; нет сетевых границ и deployment overhead.  
**Альтернатива:** микросервисы/многоагентная система. Не оправдана, пока нет нескольких независимых deployment targets или нескольких физических узлов.

## ADR-002. `STAGE/0` contracts остаются основой, но усиливаются

**Статус:** принято.  
**Решение:** сохранить текущие `Frame`, `BoardGeometry`, `CellObservation`, `BoardObservation`, `MoveHypothesis`, `MoveEvent` как концептуальные сущности; уточнить поля, validation и versioning.  
**Причина:** фундаментальный data model уже реализован и покрыт тестами.  
**Последствие:** не создавать второй параллельный формат. Миграции делать с `schema_version`.

## ADR-003. Двухстадийная схема локализации доски (Coarse-to-Fine: YOLO + Hough/RANSAC)

**Статус:** принято.  
**Решение:** двухстадийный гибридный контур:
1. Coarse BBox ROI через легковесную модель YOLOv8n-board (отсечение $80\text{--}90\%$ фонового шума стола и комнаты);
2. Субпиксельное уточнение 4 углов сетки через Canny/Hough/clustering/intersections/RANSAC внутри вырезанного ROI (алгоритм на базе `chesscog`).
3. Для синтетического кадра (Stage 0) или калиброванного стенда этап YOLO может пропускаться с прямым запуском Hough/RANSAC. Ручной ввод 4 углов сохраняется как fallback.  
**Причина:** в неконтролируемых домашних/клубных условиях на текстурированных деревянных столах прямое применение преобразования Хафа к $1920 \times 1080$ кадру даёт сотни паразитных линий. С другой стороны, нейросетевой BBox сам по себе не обеспечивает субпиксельной точности углов для корректной гомографии. Сочетание даёт максимальную помехоустойчивость и точность ($\le 2$ px).  
**Отклонённый вариант:** поиск углов исключительно чистым Canny/Hough по всему кадру без изоляции ROI доски.

## ADR-004. ArUco не обязателен

**Статус:** принято.  
**Решение:** ArUco markers — optional calibration fixture только для controlled capture/test.  
**Причина:** требование — обычная шахматная доска, без обязательной модификации сцены.  
**Основа идеи:** `mulac/chess-vision` применяет четыре ArUco marker с разными ID для локализации.  
**Отклонённый вариант:** требовать markers в каждой пользовательской игре.

## ADR-005. MediaPipe — только hand/occlusion advisory component

**Статус:** принято условно; можно отключить при низкой CPU performance.  
**Решение:** MediaPipe Hand Landmarker только обнаруживает landmarks руки. Верхний уровень строит приближённую маску/полигон и occlusion ratios клеток.  
**Причина:** рука — временная помеха; не нужно обучать свою модель рук для первой версии.  
**Ограничение:** landmarks не эквивалентны pixel-accurate segmentation.  
**Fallback:** motion detector + conservative FSM; detector failure не считать no-hand.

## ADR-006. Cell classification после rectification, не full-board detector

**Статус:** принято для baseline.  
**Решение:** нормализовать доску → извлечь 64 crops → batch classifier.  
**Причина:** известна клетка, классов мало, labels легко получить из FEN/PGN после alignment.  
**Альтернатива:** YOLO instance detection — включить, если фигуры систематически находятся между клетками или клеточные crops теряют фигуры.

## ADR-007. Multi-head EfficientNet-B0 — основной ML baseline; ResNet18 — контрольный

**Статус:** принято для первого benchmark, не окончательно по качеству.  
**Решение:** pretrained backbone + heads occupancy/type/color, сравнить с ResNet18 и 13-class single head.  
**Причина:** декомпозирует ошибки на occupancy/type/color, позволяет маскировать type/color для пустых клеток.  
**Риск:** условная независимость head outputs. Если она вредна, перейти к joint/single-head.

## ADR-008. `UNKNOWN` лучше ошибочного argmax

**Статус:** принято.  
**Решение:** occluded/low-quality cell не принуждается к одному из 13 классов.  
**Причина:** false commit намного дороже, чем задержка и ручная коррекция.  
**Последствие:** потребуются uncertainty/occlusion поля и acceptance gate.

## ADR-009. Legal move filtering через python-chess

**Статус:** принято.  
**Решение:** candidate list строится из legal moves текущей подтверждённой позиции, а каждый кандидат применяется к копии board для сравнения с observation.  
**Причина:** официальные правила уже реализованы и покрывают special moves.  
**Ограничение:** legal move не доказывает физическое действие; нужно визуальное/временное evidence.

## ADR-010. Stockfish только после confirmed move

**Статус:** принято.  
**Решение:** analysis запускается асинхронно после commit.  
**Причина:** анализ оценивает chess quality, а не достоверность camera perception.  
**Отклонённый вариант:** использовать engine score для выбора между визуальными кандидатами как основной метод.

## ADR-011. JSONL + PGN + evidence files для первой версии

**Статус:** принято.  
**Решение:** append-only JSONL event log, PGN projection, evidence files. SQLite можно добавить позже.  
**Причина:** простой replay, аудит, меньше инфраструктуры.  
**Ограничение:** сложные запросы/редактирование партий появятся позже; атомарная запись и idempotency обязательны.

## ADR-012. Synthetic Stage0 — тестовый источник, не реальный ML corpus

**Статус:** принято.  
**Решение:** использовать для deterministic integration tests, FSM и failure injection. Для piece classifier использовать реальный/3D-релевантный dataset.  
**Причина:** текущий генератор рисует плоские буквенные маркеры, не физические силуэты.

## ADR-013. Split dataset по set/session

**Статус:** принято.  
**Решение:** все crops одной board set/session остаются в одном split.  
**Причина:** предотвратить утечку почти идентичных изображений и корректно измерить generalization.

## ADR-014. Не обещать произвольный угол или любой chess set

**Статус:** принято.  
**Решение:** целевую область применимости определить измерениями. На неподдерживаемом ракурсе/сильной окклюзии система возвращает degraded/uncertain.  
**Причина:** projective transform не устраняет 3D parallax, а classifier зависит от распределения training data.

## ADR-015. Внедрение MLflow Tracking Server и Model Registry для экспериментов

**Статус:** принято.  
**Решение:** использовать MLflow для логирования параметров обучения (`backbone`, `lr`, `optimizer`, `seed`, `dataset_version`), метрик по эпохам (`train/val loss`, `val accuracy`, `macro F1`), артефактов (тепловая карта матрицы ошибок 13×13, классификационный отчёт) и сохранения чекпоинтов.  
**Причина:** академическая строгость выпускной работы, необходимость прямого сравнительного анализа разрабатываемых моделей с baseline `chesscog`, контроль воспроизводимости при обучении на бесплатных GPU-сессиях (Kaggle/Colab).

## ADR-016. Высокопроизводительный рантайм-инференс через ONNX Runtime на CPU

**Статус:** принято.  
**Решение:** обученные модели PyTorch конвертируются в оптимизированный формат ONNX (`torch.onnx.export`) с поддержкой инструкций AVX2/AVX-512 для выполнения на CPU.  
**Причина:** инференс батча из 64 клеток в чистом PyTorch на CPU требует $80\text{--}150$ мс, что вызывает деградацию видеопотока до $6\text{--}10$ FPS. ONNX Runtime сокращает задержку батча до $\le 15\text{--}20$ мс, полностью удовлетворяя требованию пояснительной записки ($\le 100$ мс на кадр, разд. 2.4.2) и обеспечивая работу в реальном времени ($15\text{--}30$ FPS) на обычном пользовательском ПК без дискретной GPU.

## ADR-017. Использование предобученных весов и датасета chesscog в качестве Baseline 0

**Статус:** принято.  
**Решение:** интеграция опубликованных весов `occupancy_classifier` и `piece_classifier` (Wölflein & Arandjelović, 2021) через `download_model.py` и использование их 5 000 3D-рендеров в комбинированном датасете.  
**Причина:** даёт немедленную работоспособность vision-контура в режиме Zero-Shot до завершения обучения собственных моделей, позволяет параллельно отлаживать FSM и контур принятия решений (Stage 2 / Stage 4), а также выступает эталонным научным ориентиром в абляционных исследованиях.

## ADR-018. Пакетный инференс для 64 клеток

**Статус:** принято.  
**Решение:** отправлять кропы всех клеток доски единым батчем размером 64 (`[64, 3, 112, 112]`) на вход ONNX Runtime.  
**Причина:** пакетная обработка на векторных инструкциях CPU выполняется в разы эффективнее, чем 64 последовательных одиночных вызова.  
**Ограничение:** при стабильной доске и отсутствии движения полный инференс 64 клеток не вызывается на каждом видеокадре, экономя ресурсы процессора.
