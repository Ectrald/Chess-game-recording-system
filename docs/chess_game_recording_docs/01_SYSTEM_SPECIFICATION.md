# 01. Системная спецификация

## 1. Назначение

Chess Game Recording System — настольная гибридная интеллектуальная система, которая получает видеопоток с обычной шахматной доски, восстанавливает последовательность физических ходов, проверяет полученные переходы формальными шахматными правилами, сохраняет игру в цифровом формате и предоставляет дополнительные аналитические сведения.

Система предназначена для регистрации партий без встроенных электронных датчиков в доске и без обязательной модификации фигур. Внешняя камера может быть USB-камерой, IP-камерой, камерой ноутбука или записанным видеофайлом. Режим источника не должен менять логику верхнего уровня.

Система не является шахматным движком и не определяет физический ход исключительно по оценке Stockfish. Основная функция — установить, какой ход был фактически сделан. Шахматный движок анализирует уже подтверждённые позиции и ходы.

## 2. Цели продукта

1. Автоматически получать изображения обычной шахматной доски из видео.
2. Определять положение доски, её перспективу и координатную ориентацию.
3. Восстанавливать вероятностное содержимое 64 клеток.
4. Отличать стабильную позицию от промежуточных кадров движения, руки и теней.
5. Сопоставлять визуальные наблюдения с допустимыми ходами из текущей подтверждённой позиции.
6. Не фиксировать ход, если доказательств недостаточно; запрашивать дополнительные кадры или помощь пользователя.
7. Сохранять последовательность в PGN и обеспечивать восстановление сеанса после сбоя.
8. По запросу выполнять последующий шахматный анализ, не блокируя видеорегистрацию.
9. Предоставлять объяснимую историю принятия решения: что изменилось, какие кандидаты рассматривались, почему ход был принят или отклонён.

## 3. Границы системы

### 3.1. Входит в систему

- приём видеоданных из файла, камеры или сетевого источника;
- локализация шахматной доски и контроль качества геометрии;
- преобразование перспективы и привязка клетки к координате `a1`…`h8`;
- обнаружение рук и оценка перекрытия клеток;
- обнаружение движения и стабилизация наблюдений во времени;
- ML-распознавание пустоты/типа/цвета фигуры;
- представление текущей позиции и истории партии;
- генерация кандидатов ходов и проверка legal moves;
- отложенное принятие решения, повторная обработка и ручное подтверждение;
- экспорт FEN/PGN;
- асинхронная оценка позиции и качества хода шахматным движком;
- диагностические журналы и benchmark.

### 3.2. Не входит в базовую версию

- определение силы/личности игроков;
- распознавание часов, жестов и эмоций игроков;
- автоматический судейский контроль по всем правилам соревнований;
- определение точного трёхмерного положения фигуры в пространстве;
- универсальная поддержка произвольных абстрактных шахматных фигур;
- поддержка нескольких досок в одном кадре;
- работа при полностью закрытой доске;
- гарантированная работа с камерой, которая не видит хотя бы большую часть границ доски;
- автоматическое исправление неверной физической позиции путём изменения официальной записи без фиксации причины.

## 4. Режимы работы

| Режим | Вход | Результат | Ограничения |
|---|---|---|---|
| Видео-файл | MP4/AVI или другой поддерживаемый контейнер | PGN, журнал событий, отчёт benchmark/анализа | Можно выполнять seek и воспроизводить ошибки детерминированно |
| Live-камера | USB/WebCam/IP stream | Текущий ход, позиция, PGN и предупреждения | Нужны буферизация и контроль потерянных кадров |
| Пошаговая отладка | Кадры или synthetic sequence | Объяснимый выход каждого pipeline stage | Предназначено для разработчика |
| Synthetic test | PGN + параметры генератора | Повторяемый поток с ground truth | Не заменяет real-world dataset |
| Анализ сохранённой партии | PGN/FEN или список MoveEvent | Оценка позиции, лучший вариант, отчёт об ошибках | Не меняет фактическую запись партии |

## 5. Пользователи и внешние системы

- **Оператор/игрок:** запускает и останавливает сессию, выбирает видеоисточник, подтверждает стартовую позицию/ориентацию, разрешает неоднозначности.
- **Аналитик:** просматривает PGN, FEN, оценку позиций, объяснения и evidence.
- **Разработчик/тестировщик:** запускает диагностические режимы, benchmark, просмотр промежуточных данных и профилирование.
- **Источник видео:** поставляет кадры и timestamp.
- **Шахматный движок:** получает подтверждённые позиции для последующего анализа.

## 6. Основные пользовательские сценарии

### UC-01. Запуск новой сессии

**Предусловия:** доступен источник видео; пользователь запускает систему.  
**Основной поток:** открыть источник → проверить поток → найти доску → оценить геометрию → определить ориентацию → получить начальное/текущее состояние → запросить подтверждение, если позиция не может быть восстановлена однозначно → создать Session.  
**Альтернативы:** источник не открыт; доска не найдена; геометрия нестабильна; ориентация неизвестна; доска частично закрыта.  
**Постусловие:** сессия находится в `STABLE` либо ждёт калибровки/подтверждения.

### UC-02. Регистрация хода

**Предусловия:** сессия активна, имеется подтверждённая позиция `B_t`.  
**Основной поток:** получить кадры → проверить геометрию и occlusion → измерить motion → при начале движения заморозить официальную позицию → дождаться стабилизации → построить вероятностное наблюдение → получить список legal moves из `B_t` → оценить кандидатов → принять единственный уверенный вариант → записать событие и обновить состояние.  
**Альтернативы:** несколько кандидатов близки по оценке; ни один кандидат не согласуется с наблюдением; фигура возвращена на исходную клетку; наблюдение частично закрыто.  
**Постусловие:** либо создан один подтверждённый `MoveEvent`, либо система остаётся в `UNCERTAIN` без изменения позиции.

### UC-03. Разрешение неоднозначности

**Предусловие:** кандидаты неразличимы по confidence margin или нет допустимого перехода.  
**Основной поток:** сохранить top-K hypotheses и evidence → попросить дополнительные кадры → повторно обработать только затронутые клетки → пересчитать кандидатов → при необходимости показать оператору спорные клетки и варианты → получить ручное подтверждение/коррекцию.  
**Постусловие:** восстановлена согласованная позиция либо сессия остаётся приостановленной.

### UC-04. Анализ хода

**Предусловие:** ход зафиксирован и имеет FEN до/после.  
**Основной поток:** отправить задачу в ограниченную очередь → движок оценивает позицию до и после → определить изменение оценки с учётом стороны хода → сохранить PV/best move/eval → показать пользователю.  
**Альтернативы:** движок выключен, недоступен, превышен timeout, очередь переполнена.  
**Постусловие:** регистрация не откатывается; analysis status может иметь `FAILED` или `SKIPPED`.

### UC-05. Экспорт партии и восстановление

Пользователь сохраняет PGN, JSONL-журнал и evidence. После сбоя система восстанавливает последнюю подтверждённую позицию из журнала событий, проверяет цепочку `fen_before → move → fen_after` и не дублирует последний ход.

## 7. Функциональные требования

| ID | Требование | Приёмочный критерий |
|---|---|---|
| FR-01 | Принимать файл, устройство или сетевой видеопоток через единый контракт | Источник заменяется конфигурацией без изменения vision/reasoning API |
| FR-02 | Каждому кадру назначать id и timestamp | id монотонно растёт; timestamp не убывает и сохраняет источник времени |
| FR-03 | Находить доску или использовать ручную калибровку как fallback | При низком качестве геометрии ходы не регистрируются |
| FR-04 | Нормализовать геометрию доски | Матрица преобразования и качество доступны в `BoardGeometry` |
| FR-05 | Устанавливать ориентацию координат | `a1`…`h8` сопоставлены однозначно либо статус `UNKNOWN` |
| FR-06 | Формировать 64 клеточных наблюдения | Каждый снимок содержит ровно 64 клетки и полный алфавит классов |
| FR-07 | Возвращать вероятности, а не только argmax | Верхний уровень получает distribution + confidence/uncertainty |
| FR-08 | Отмечать перекрытые клетки | Каждая клетка имеет occlusion ratio/validity |
| FR-09 | Не менять позицию во время движения | FSM не публикует `MoveEvent` до окончания settle/verify |
| FR-10 | Проверять кандидаты относительно легальных ходов | Нелегальный переход не может быть committed |
| FR-11 | Поддерживать специальные ходы | Castling, en passant и promotion проходят end-to-end tests |
| FR-12 | Не фиксировать неоднозначность автоматически | При низком score или малом margin состояние `UNCERTAIN` |
| FR-13 | Сохранять подтверждённые ходы | Для каждого события имеются FEN до/после, UCI, SAN, timestamp и evidence ref |
| FR-14 | Экспортировать PGN | PGN воспроизводит подтверждённую последовательность ходов |
| FR-15 | Анализировать ходы в фоне | Таймаут Stockfish не блокирует frame capture и не меняет игровое состояние |
| FR-16 | Обеспечивать ручную коррекцию | Коррекция сохраняется как отдельное auditable событие |
| FR-17 | Вести журнал отказов | Ошибка имеет тип, компонент, timestamp и контекст |

## 8. Нефункциональные требования

### 8.1. Надёжность

- Не принимать решение по одному кадру.
- Не изменять official game state на основании низкокачественной геометрии или критической окклюзии.
- Все изменения партии выполнять атомарно.
- При потере источника сохранять последнюю подтверждённую позицию.
- Любой необработанный сбой vision/engine должен переводить соответствующий контур в degraded/failed, но не повреждать журнал.

### 8.2. Устойчивость к вариативности

Начальная область испытаний: обычные Staunton-подобные наборы, несколько досок/материалов, умеренные углы съёмки, несколько условий освещения. Целевой диапазон ракурсов задаётся как угол камеры относительно плоскости доски; он должен быть измерен экспериментально. Нельзя заявлять «любая камера» или «любой угол» без соответствующего набора тестов.

### 8.3. Производительность

- Захват кадра не должен ожидать Stockfish.
- ML inference должен обрабатывать клетки пакетно.
- Очереди должны иметь фиксированные пределы и политику переполнения.
- Для live-видео допустим пропуск промежуточных кадров для inference, но timestamp и порядок подтверждённых ходов должны сохраняться.
- Реальные target FPS/latency определить после профилирования на CPU и доступной GPU.

### 8.4. Переносимость и стоимость

Обучение ML должно быть возможно на бесплатных/ограниченных GPU-сессиях Kaggle: pretrained backbone, transfer learning, checkpoint/resume, фиксированные seed, небольшой датасет с эффективной аугментацией. Runtime не должен требовать GPU, если CPU-скорость достаточна для сценария.

### 8.5. Объяснимость

Для каждого accepted/rejected move должны сохраняться score components, top alternatives, changed squares, occluded squares, geometry quality и reason code. Пользователь должен отличать «ход распознан», «ход предположен», «позиция не определена» и «анализ движка завершён».

## 9. Формальные правила принятия решения

1. Подтверждённая позиция `B_t` — единственный источник правды для партии.
2. ML выдаёт наблюдение, а не официальный ход.
3. Наблюдение может быть неполным; неизвестные/закрытые клетки не трактуются как empty.
4. Кандидат хода рассматривается только из legal moves текущей позиции.
5. Кандидат оценивается по визуальному совпадению затронутых клеток и по устойчивости нескольких кадров.
6. Если absolute score ниже порога, margin между top-1 и top-2 недостаточен или затронуты клетки с критической окклюзией, решение откладывается.
7. Коммит хода выполняется только после повторного вычисления SAN/FEN с помощью шахматной библиотеки.
8. Stockfish не может легализовать нелегальный ход и не заменяет физическое наблюдение.
9. При восстановлении после сбоя журнал событий проверяется как цепочка переходов.

## 10. Критерии успешности продукта

Показатели оцениваются на зафиксированном test set, отделённом по наборам фигур и сессиям:

- `committed_move_precision` — доля верно подтверждённых ходов среди всех автоматически подтверждённых;
- `move_recall` — доля эталонных ходов, зарегистрированных системой (ручные corrections учитывать отдельно);
- `false_commit_rate` — доля неверно подтверждённых ходов;
- `uncertain_rate` — доля ходов, переданных на дополнительную обработку/пользователю;
- `game_exact_match` — доля партий с полным совпадением move sequence;
- `median_move_latency`, `p95_move_latency`;
- `manual_intervention_rate`;
- `recovery_success_rate` после кратковременных помех/потери кадра.

Приоритет качества: минимизация false commits важнее максимизации доли автоматического принятия. Система может запросить помощь оператора; тихо добавить неправильный ход — недопустимо.
