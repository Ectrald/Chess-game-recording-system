# 04. Проектирование контура компьютерного зрения

## 1. Цель и выход

Vision-контур преобразует исходный кадр в проверяемое вероятностное описание 64 клеток. Он не принимает официальные шахматные решения.

Вход: `Frame`.  
Основной выход: `BoardObservation` или явный статус ошибки/неопределённости.  
Промежуточные артефакты: `BoardGeometry`, нормализованное изображение, 64 ROI, маска руки, motion map, raw model probabilities.

## 2. Рекомендуемый pipeline

```text
Frame
  → quality gate / resize
  → board localization
  → quadrilateral refinement
  → geometry validation
  → homography / canonical board image
  → orientation resolution
  → cell ROI extraction
  → hand + motion observation
  → batched cell classifier
  → BoardObservation
```

Все стадии должны иметь диагностический режим, сохраняющий overlay: найденные углы, сетку, клетки, имя `a1`/`h8`, hand polygon, low-confidence cells.

## 3. Стадия A — предварительная оценка кадра

1. Проверить, что frame не пустой и имеет ожидаемый размер.
2. Учитывать цветовой порядок и преобразование в grayscale/RGB.
3. Оценить размытие, чрезмерную темноту/пересвет, размер доски относительно кадра.
4. Если кадр непригоден, не запускать дальнейшую детекцию и вернуть `FRAME_QUALITY_LOW`.
5. Не менять размер до board localization без сохранения scale factor для возврата координат в исходный кадр.

Начальные диагностические метрики: Laplacian variance для blur, mean/percentile brightness, clipping ratio. Это не универсальные критерии качества, пороги подбираются на реальных кадрах.

## 4. Стадия B — локализация шахматной доски (Coarse-to-Fine: YOLO + Hough/RANSAC)

### 4.1. Двухстадийный контур локализации

В реальных условиях (домашние столы с текстурой дерева, обои, клубные помещения, блики) применение чистого преобразования Хафа к полноразмерному кадру $1920 \times 1080$ приводит к ложным срабатываниям из-за обилия посторонних параллельных линий и текстурного шума. Поэтому принята двухстадийная схема **Coarse-to-Fine**:

$$\text{Кадр } (1920\times 1080) \xrightarrow{\text{YOLOv8n-board}} \text{Coarse BBox ROI} \xrightarrow{\text{Hough + RANSAC (chesscog style)}} 4 \text{ субпиксельных угла} \xrightarrow{\text{Homography}} 640 \times 640$$

1. **Стадия 1 (Coarse BBox — YOLOv8n-board):**
   - Легковесная модель детекции (YOLOv8-nano, обученная на 1 класс `board`) локализует грубый Bounding Box доски в кадре с запасом margins ($5\text{--}10\%$).
   - Выполняется быстро ($\le 8\text{--}12$ мс на CPU) и отсекает $80\text{--}90\%$ площади кадра с посторонними текстурами, руками игроков и окружающим интерьером.
   - *Примечание:* Для чистого синтетического кадра (Stage 0) или при известной геометрии камеры этап YOLO может пропускаться с передачей кадра напрямую во вторую стадию.

2. **Стадия 2 (Fine Corners — Hough + RANSAC refinement):**
   - Внутри вырезанного ROI применяется классический контур субпиксельного уточнения углов, адаптированный из исследовательского опыта `chesscog`:
     1. перевод ROI в grayscale;
     2. сглаживание Gaussian blur и детектор границ Canny;
     3. извлечение линий (вероятностное или стандартное преобразование Хафа);
     4. разделение линий на две ортогональные группы с учётом перспективы;
     5. фильтрация дубликатов и кластеризация пучков линий;
     6. нахождение точек пересечений кандидатов линий;
     7. поиск регулярной решётки $9 \times 9$ или подрешётки $8 \times 8$ с устойчивым проективным шагом;
     8. оценка проективной модели методом RANSAC для отсева выбросов;
     9. извлечение 4 внешних углов игрового поля с субпиксельной точностью (`cv2.cornerSubPix`);
     10. проверка reprojection error и confidence метрики.

### 4.2. Иерархия методов локализации

| Метод | Роль в системе | Обоснование / Ограничение |
|---|---|---|
| **YOLOv8n + Hough/RANSAC** | **Основной рабочий режим** | Сочетает помехоустойчивость детектора к окружающему фону с субпиксельной точностью Хафа/RANSAC |
| **Pure Hough + RANSAC** | **Режим для синтетики / чистых стендов** | Быстрый детерминированный прогон без нейросетевых зависимостей (активен в синтетическом генераторе Stage 0) |
| **Ручной выбор 4 углов** | **Fallback / Калибровка стенда** | Гарантированная фиксация гомографии пользователем при экстремальных ракурсах или нестандартных досках |
| **ArUco-маркеры** | **Лабораторная калибровка / Ground Truth** | Используется в исследовательских сессиях (опыт `chess-vision`) для верификации субпиксельной точности |

**Не рекомендовано на старте:** обучать end-to-end detector фигур по всему изображению. Ошибки геометрии и piece classification станут плохо разделимыми.

### 4.3. Геометрическое качество

Проверять:

- выпуклость и отсутствие самопересечений четырёхугольника;
- достаточно большую площадь и разрешение;
- адекватность длин противоположных сторон после rectification;
- reprojection error по найденным линиям/intersections;
- устойчивость углов от кадра к кадру;
- отсутствие чрезмерного clipping краёв доски.

Соседние кадры не должны давать резко меняющуюся гомографию при неподвижной камере. Фильтрация геометрии по времени разрешена, но smoothing не должен скрывать реальное смещение камеры.

## 5. Стадия C — гомография и ориентация

### 5.1. Нормализация

После определения углов строится homography в квадрат `target_board_size × target_board_size` (первичный размер 640×640 уже фигурирует в конфигурации). Преобразование нужно для координатной сетки, но не является физической коррекцией высоты фигур.

### 5.2. Ориентация

Ориентация — дискретное отображение нормализованной сетки на шахматные координаты (какой из четырёх углов соответствует полю `a1`). Углы доски без маркировки симметричны. Правило «правое нижнее поле белое» помогает разделить пространство поворотов на пары $\{0^\circ, 180^\circ\}$ и $\{90^\circ, 270^\circ\}$, но само по себе чередование клеток не отличает направление $0^\circ$ от $180^\circ$.

Для надёжного автоматического и полуавтоматического разрешения ориентации принят трёхфакторный подход:

1. **Геометрический тест цвета угла (Color Check):**
   - Поле в правом нижнем углу нормализованного изображения обязано быть светлым (`h1` для вида со стороны белых, `a8` для вида со стороны чёрных). Это однозначно исключает повороты на $90^\circ$ и $270^\circ$.
2. **Анализ градиентной/визуальной массы фигур (Mass & Color Distribution):**
   - В начальной расстановке и большинстве дебютных/миттельшпильных позиций 1-я и 2-я горизонтали содержат белый лагерь (светлые фигуры), а 7-я и 8-я — чёрный лагерь (тёмные фигуры).
   - Сравнение распределения средней интенсивности пикселей и градиентной плотности между нижними (1–2) и верхними (7–8) рядами нормализованной доски позволяет надёжно различить ориентацию $0^\circ$ (белые внизу) и $180^\circ$ (чёрные внизу).
3. **Явная конфигурация пользователя / проверка стартовой позиции:**
   - Если пользователь указал сторону («камера со стороны белых» или «со стороны чёрных»), принимается явное значение без эвристик.
   - Если партия начинается со стандартной расстановки, классификатор фигур проверяет расположение королей/ферзей на 1-й и 8-й горизонталях.
   - *Критическое правило:* пока ориентация не подтверждена с высокой достоверностью, FSM блокирует формирование SAN/PGN-записи и не фиксирует ходы.

### 5.3. Качество и drift

Для неподвижной камеры первичная гомография может быть постоянной. Тем не менее периодически проверять стабильность доски. Если углы сместились выше порога, пересчитать geometry; если смещение камеры велико, FSM переходит в `BOARD_LOST`/`RECALIBRATING`.

## 6. Стадия D — выделение клеток и учёт высоты фигур

После нормализации доска делится на сетку 8×8. Простое crop ровно по квадрату клетки часто обрезает верхнюю часть/боковые контуры фигур, особенно при перспективе.

Рекомендуемый crop для классификатора должен включать:

- базовую область клетки;
- дополнительный вертикальный контекст вверх, зависящий от ряда/ракурса;
- небольшой контекст соседних клеток, если это уменьшает ошибку параллакса;
- фиксированное итоговое resize для backbone.

Параметр расширения (`parallax_height_alpha`) из Stage 0 допустим как initial experiment, но не должен фиксироваться как универсальная константа 1.25 без измерения. Подбирать crop policy по реальным фото/видео с held-out camera angle.

**Важно:** высокие фигуры могут выступать за пределы клетки в rectified 2D изображении. Поэтому оценивать не только cell-level crops, но и альтернативы:

- position-aware crop (Chesscog style) с увеличением области выше клетки;
- base-focused crop (контур/деталь основания);
- shared context crop с соседними полями;
- ensemble двух crop views для трудных клеток.

В MVP выбрать position-aware crop и сохранить возможность настройки по ряду/столбцу.

## 7. Стадия E — обнаружение руки и окклюзии

### 7.1. MediaPipe Hand Landmarker

MediaPipe выполняет одну узкую задачу: обнаруживает руку и выдаёт landmarks. Сам по себе hand landmark model не гарантирует точную сегментационную маску всей руки.

Алгоритм интеграции:

1. Конвертировать кадр BGR → RGB.
2. Запустить Hand Landmarker в IMAGE/VIDEO/LIVE_STREAM режиме в зависимости от режима приложения.
3. Получить landmarks и hand bounding region.
4. Преобразовать landmarks в координаты исходного кадра.
5. Построить convex hull по landmarks, расширить его на safety margin; при наличии подходящего segmentation output использовать его вместо hull.
6. Перевести polygon в normalized board coordinates через `H_image_to_board`.
7. Для каждой клетки вычислить долю пересечения `occlusion_ratio`.
8. Установить status и confidence детектора.

Если MediaPipe не обнаружил руку, это не всегда означает, что руки нет: hand detector может пропустить руку, которая видна частично или закрывает только участок. Поэтому дополнительно использовать motion/appearance cues.

### 7.2. Резервный режим

При `UNAVAILABLE/ERROR`:

- не считать все клетки гарантированно свободными от руки;
- использовать motion score и резкое локальное изменение яркости;
- увеличить stable window;
- снизить допустимость автоматического commit при подозрении на occlusion;
- пометить evidence причиной `HAND_DETECTOR_UNAVAILABLE`.

MediaPipe может обрабатываться реже, чем каждый видеокадр, например на каждом N-м кадре/целевом FPS. Частота определяется профилированием CPU. Vision pipeline не должен зависеть от MediaPipe как от единственной точки отказа.

## 8. Стадия F — motion detection

Начальный метод: frame differencing в rectified board space.

1. Перевести board image в grayscale.
2. Компенсировать глобальные изменения экспозиции/яркости (например, оценкой среднего изменения вне динамических областей).
3. Применить Gaussian blur.
4. Вычислить absolute difference текущего и предыдущего кадра.
5. Применить threshold, morphology open/close.
6. Вычислить общую и поклеточную долю изменившихся пикселей.
7. Объединить с hand occlusion status.
8. Сгладить score temporal window.

Не полагаться на motion как на детектор хода: тень может выглядеть как движение, неподвижная рука может не давать motion, а автоматический баланс белого может менять большую часть кадра. Motion — сигнал FSM, а не событие `MoveEvent`.

Дополнительные варианты:

- optical flow (Farneback/LK) — полезен для направления движения, но более дорогой;
- background subtraction — возможен для фиксированной камеры, менее устойчив к освещению;
- feature tracking — использовать для стабилизации камеры, если она шевелится.

## 9. Стадия G — классификация клеток

### 9.1. Основная модель

Рекомендуемая начальная конфигурация: один pretrained EfficientNet-B0 backbone и три независимые головы:

- occupancy: `empty / occupied`;
- piece type: `pawn / knight / bishop / rook / queen / king`;
- color: `white / black`.

Для пустых клеток type/color heads не должны считаться значимыми. Вероятности полного 13-классового пространства собираются как:

```text
P(empty) = 1 - P(occupied)
P(w_piece_type, w_color) = P(occupied) × P(type) × P(color)
P(b_piece_type, b_color) = P(occupied) × P(type) × P(color)
```

Это factorized approximation и предполагает условную независимость головы типа и цвета при заданной занятости. Её необходимо сравнить с single-head 13-class baseline. Если независимость приводит к конфликтам, использовать single-head или joint head.

### 9.2. Почему не object detector для каждой фигуры

После rectification координаты клетки известны. Поэтому cell classifier получает конкретный crop и решает ограниченную классификационную задачу; для первой версии нет смысла размечать bounding boxes каждой фигуры. Object detector остаётся альтернативой, если фигуры часто стоят между клетками или смещены относительно поля.

### 9.3. Выбор моделей и baseline-архитектур

1. **Baseline 0 (Pretrained chesscog — Wölflein & Arandjelović, 2021):**
   - Готовые веса двухэтапной классификации (`occupancy_classifier` + `piece_classifier`), обученные на 5 000 3D-рендеров.
   - Используются для немедленного сквозного тестирования vision-пайплайна («zero-shot» на синтетике и реальных досках) и служат научной точкой отсчёта для сравнения с нашими моделями.
2. **Основная модель (Baseline 1 — Multi-head EfficientNet-B0):**
   - Pretrained ImageNet с дообучением на комбинированном датасете. Отличное соотношение macro F1 / latency.
3. **Контрольная модель (Baseline 2 — ResNet-18):**
   - Устойчивая архитектура для абляционных исследований и воспроизведения структуры `chesscog`.
4. **Легковесная альтернатива (MobileNetV3-Small):**
   - При жёстких ограничениях по ресурсам CPU мобильных/встроенных платформ.

### 9.4. Инференс и аппаратно-программная оптимизация (ONNX Runtime)

Вход: batch-тензор `[64, 3, H, W]` всех клеток доски после нормализации и кропа.  
Выход: матрицы вероятностей для 64 клеток (`[64, 13]`).

- **Критичность latency:** Инференс батча из 64 клеток в чистом PyTorch на CPU занимает $80\text{--}150$ мс, что снижает пропускную способность видеопотока до $6\text{--}10$ FPS и вызывает пропуски фаз постановки руки.
- **ONNX Runtime (CPU Execution Provider):** Экспорт обученных PyTorch-весов в формат ONNX с оптимизацией графа (constant folding, operator fusion) сокращает время инференса батча из 64 клеток до $\mathbf{\le 15\text{--}20}$ **мс** на CPU (Intel Core i5/i7 или аналоги).
- Это обеспечивает целевой темп работы системы в реальном времени ($15\text{--}30$ FPS) без обязательного наличия дискретной GPU на пользовательской машине. Экспорт в ONNX и бенчмаркинг latency входят в стандартный MLOps-пайплайн (Stage 3).

## 10. Сбор датасета и crop labeling

Источники:

1. 3D-рендеры chesscog dataset как начальное синтетическое pretraining;
2. реальные фото отдельных комплектов и досок;
3. реальные видео с аннотацией позиции/ходов;
4. Stage0 synthetic generator — только для API/FSM/integration tests, не для обучения классификатора физических фигур.

Автоматическая нарезка из реального видео по PGN требует синхронизации времени. Сам PGN содержит последовательность ходов, но не timestamp каждого хода. Нужно:

- операторские отметки ходов, либо
- файл `move_timestamps.csv`, либо
- арбитражный alignment с motion events и ручная проверка alignment.

При разметке использовать `python-chess` для построения позиции до/после хода и обновлять все изменившиеся клетки, включая castling/en-passant/promotion. Не маркировать все клетки из произвольного кадра как текущую позицию, если кадр попал в середину движения.

### 10.1. Разбиение

Разбивать по группам, а не по отдельным crops:

- train: часть chess sets + часть camera sessions;
- validation: отдельные сессии/условия;
- test: полностью невиданные шахматные наборы и/или камера.

Нельзя помещать соседние кадры одного видео в train и test: почти идентичные картинки дают утечку данных.

## 11. Аугментации

Полезные:

- brightness/contrast/gamma/white balance;
- mild hue/saturation;
- gaussian/motion blur;
- JPEG/compression noise;
- sensor noise;
- soft shadows;
- partial occlusion cutout;
- perspective/scale/position-aware transforms;
- anchored shear/scale, где основание фигуры сохраняет контакт с плоскостью поля.

Осторожно с rotation: поворот только crop картинки может физически менять положение основания относительно клетки. Также нельзя чрезмерно деформировать фигуры, уничтожая различия типа.

## 12. Критерии качества vision

Измерять отдельно:

- board corner reprojection error;
- board orientation accuracy;
- cell crop coverage/position error;
- macro F1 по 13 классам;
- per-class precision/recall;
- calibration error вероятностей;
- cell accuracy на unseen set;
- full-board exact accuracy (все 64 клетки правильно);
- latency per stage;
- rate `unknown/occluded`.

Главная vision метрика не только cell accuracy: 64 независимых решения на одной доске увеличивают вероятность ошибки полного состояния. Далее reasoning должен уметь использовать uncertainty и legal move constraints, а не требовать безошибочного argmax каждой клетки.
