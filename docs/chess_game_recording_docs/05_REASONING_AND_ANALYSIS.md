# 05. Логико-символьный контур, регистрация ходов и шахматная аналитика

## 1. Ответственность reasoning-контура

Reasoning получает последовательность вероятностных `BoardObservation`, текущую подтверждённую позицию и quality signals. Он определяет, можно ли интерпретировать наблюдение как один конкретный физический шахматный ход. Контур не пытается реконструировать всю игру с нуля по каждому кадру и не принимает победителя по оценке Stockfish.

Ключевой принцип: **официальная позиция изменяется только после подтверждения legal move**. Любая неопределённость сохраняет предыдущее состояние.

## 2. Конечный автомат сессии

Рекомендуемые состояния:

| Состояние | Смысл | Допустимые действия |
|---|---|---|
| `NO_SOURCE` | Видеоисточник не открыт | Открыть источник, показать ошибку |
| `LOCATING_BOARD` | Поиск доски | Детекция, ручной выбор углов |
| `CALIBRATING` | Уточнение ориентации/стартовой позиции | Запрос пользователя, анализ стандартной расстановки |
| `STABLE` | Доска стабильна, есть confirmed position | Собирать кадры, следить за движением |
| `MOVING` | Движение обнаружено | Не запускать commit; собирать дополнительные кадры |
| `SETTLING` | Движение прекратилось, ожидается стабилизация | Debounce window, проверять руку и motion |
| `VERIFYING` | Есть достаточно стабильных observations | Построить candidate moves, оценить |
| `UNCERTAIN` | Не хватает уверенности/нет согласованного хода | Recovery, дополнительные кадры, ручное подтверждение |
| `BOARD_LOST` | Доска потеряна/геометрия сломалась | Re-detect, recalibrate |
| `PAUSED` | Пауза оператора | Остановить commit и live analysis |
| `STOPPED` | Сессия закрыта | Flush журнал, закрыть ресурсы |

Упрощённый переход:

```text
NO_SOURCE → LOCATING_BOARD → CALIBRATING → STABLE
STABLE → MOVING → SETTLING → VERIFYING
VERIFYING → STABLE       (кандидат принят и закоммичен)
VERIFYING → UNCERTAIN    (неоднозначно/нет кандидата)
UNCERTAIN → VERIFYING    (новые observations)
UNCERTAIN → STABLE       (ручное подтверждение/коррекция)
любое активное состояние → BOARD_LOST / PAUSED / STOPPED
BOARD_LOST → LOCATING_BOARD
```

Не использовать одно большое состояние для всего приложения: у analysis job должен быть отдельный lifecycle `QUEUED/RUNNING/COMPLETED/FAILED/SKIPPED`.

## 3. Временная стабилизация

### 3.1. Входные признаки

На каждом выбранном кадре собираются:

- global motion score;
- local motion score по клеткам;
- hand detector status/regions;
- geometry quality и её изменение относительно предыдущих кадров;
- число reliable cells;
- изменение вероятностей cell classifier;
- длительность неподвижности.

### 3.2. Политика

1. В `STABLE` любое превышение motion threshold переводит FSM в `MOVING`.
2. В `MOVING` официальная позиция не изменяется. Vision может работать с меньшей частотой/собирать evidence.
3. Когда motion снизился, перейти в `SETTLING`.
4. Выждать `settling_time_sec` и требовать несколько последовательных кадров со стабильной геометрией и небольшим motion.
5. Если рука перекрывает клетки, относящиеся к кандидатам, окно продлевается или система ждёт удаления руки.
6. При стабильности перейти в `VERIFYING` и получить одно или несколько полных observations.
7. В случае слишком большого интервала без стабильности/потери доски — `UNCERTAIN` или `BOARD_LOST`.

Начальное значение `settling_time_sec=0.8` из Stage0 — стартовая гипотеза. Оно должно настраиваться по реальному видео; длительное ожидание увеличивает latency, слишком короткое приводит к ложным позициям.

## 4. Сравнение позиций и генерация кандидатов

### 4.1. Почему не argmax полного board state

Если по каждой клетке взять только наиболее вероятную метку, одна ошибка на одной клетке может привести к невалидной позиции. Также часть клеток может быть закрыта рукой. Поэтому reasoning должен использовать вероятности и знать, какие клетки надёжны.

### 4.2. Генерация кандидатов

1. Имеется последняя подтверждённая позиция `B_t`.
2. Сгенерировать список `legal_moves(B_t)` через `python-chess`.
3. Для каждого кандидата `m` скопировать board, выполнить `push(m)`, получить ожидаемую позицию `B_m`.
4. Получить множество затронутых клеток `A(m)` из разницы фактического placement до/после и специальных move semantics.
5. Оценить вероятностное согласование `B_m` с `BoardObservation` только по reliable клеткам, но также учитывать глобальные противоречия, если они не occluded.
6. Добавить temporal/geometry/occlusion scores.
7. Упорядочить кандидатов по общему score.

Это эффективно: рассматриваются legal moves текущей позиции, а не произвольные 64-клеточные конфигурации.

### 4.3. Визуальное правдоподобие

Для кандидата `m` с ожидаемой фигурой `p_m(s)` на клетке `s` можно использовать логарифмическое правдоподобие:

\[
S_v(m)=\frac{1}{|R(m)|}\sum_{s\in R(m)}\log(\max(\epsilon,P_s(p_m(s))))
\]

где `R(m)` — клетки, доступные для надёжного сравнения, `P_s` — probability vector клетки, `epsilon` защищает от `log(0)`. Для клеток, закрытых рукой или имеющих `is_reliable=False`, likelihood не считается как отрицательное доказательство.

Для повышения устойчивости можно отдельно оценивать:

- `S_affected`: совпадают ли клетки, затронутые ходом (с факторизацией `occupancy + color`, чтобы в Zero-Shot / при нестандартной фигурке не занижать вероятность до `1/6`, а также с жёстким штрафом при противоречии хотя бы одной целевой клетки, чтобы ложный ход с тем же `from_sq` не маскировался линейным средним);
- `S_global`: нет ли значимых конфликтов в остальной части доски;
- `S_temporal`: сохраняется ли новая позиция в последующих observations.

Не включать confidence в формулу повторно, если он уже отражён в calibrated probabilities.

### 4.4. Итоговый score

Возможная первая версия:

\[
S(m)=w_v S_v(m)+w_t S_t(m)+w_g S_g-w_o P_o(m)
\]

где все слагаемые нужно привести к сопоставимой шкале. Текущие веса в `default_config.yaml` (0.50/0.25/0.15/0.10) можно использовать как начальную конфигурацию, но не как обученные оптимальные веса.

Acceptance gate использует одновременно:

- минимальное абсолютное качество `S(m_1) >= threshold_abs`;
- разницу top-1 и top-2 `S(m_1)-S(m_2) >= min_confidence_margin`;
- стабильность во времени;
- качество geometry;
- отсутствие критической occlusion затронутых клеток;
- наличие legal transition.

Если top-2 отсутствует, margin не считается бесконечным автоматически: проверить абсолютный score и число валидных evidence cells.

## 5. Специальные ходы

Не реализовывать отдельные самописные шахматные правила для push/pop ходов, если они уже поддерживаются `python-chess`. Использовать библиотеку как источник истины для:

- рокировки (`e1g1`, `e1c1`, аналогично чёрным);
- en passant;
- promotion с choice `q/r/b/n`;
- шаха, мата, пата и legal move filtering.

Топологические сигнатуры числа изменённых клеток полезны для candidate pruning/diagnostics, но не должны быть единственным признаком: например, castling изменяет четыре клетки, en-passant три, стандартный ход обычно две, но observation может пропускать изменения из-за окклюзии.

## 6. Recovery pipeline

Если кандидат не прошёл acceptance gate:

1. Не менять `B_t`.
2. Сохранить `UNCERTAIN` packet: observations, probabilities, motion, geometry, hand regions, top-K moves.
3. Получить дополнительные кадры после удаления руки/движения. При появлении нового движения в `UNCERTAIN` возвращаться в цикл `MOVING → SETTLING → VERIFYING` для повторной оценки (при падении нескольких фигур или поправке одной фигуры выдерживать короткое окно восстановления до вывода модала оператору).
4. Повторно классифицировать только затронутые/изменившиеся клетки (`Sparse Changed-Cell Inference`), если геометрия не менялась.
5. Если геометрия изменилась (наклон камеры/сдвиг стола), обновить гомографию через трекер дрифта и перепривязать опорные кадры без сброса партии; при потере доски — recalibrate geometry.
6. При 3–4 изменившихся клетках без 1-ply совпадения (быстрая серия двух ходов внутри окна дебаунса) выполнить ограниченный поиск 2-ходовой цепочки `(m_1, m_2)` через `python-chess`.
7. При физическом возврате доски в состояние до последнего закоммиченного хода в очередь соперника (`takeback`) выполнить контролируемый откат (`rollback`) с перепривязкой опорного снимка.
8. Если согласованного решения всё ещё нет, запросить пользователя и сохранить коррекцию с actor=`operator`.

Нельзя молча «подгонять» новую позицию под ближайшую legal move, если visual evidence слабое. Legal move restriction помогает устранить невозможные интерпретации, но физическая доска могла содержать ошибку/нелегальное действие/неполную позицию.

## 7. Атомарная фиксация хода

Компонент `GameStateManager.commit(move_hypothesis)` выполняет:

1. блокирует параллельную модификацию текущей позиции;
2. копирует текущий `chess.Board`;
3. проверяет, что ход legal;
4. вычисляет SAN на исходной позиции;
5. выполняет `push` на копии;
6. строит FEN до/после;
7. формирует `MoveEvent` с event_id и evidence refs;
8. записывает event в append-only log во временный файл/atomic append protocol;
9. сохраняет/проверяет evidence artifacts;
10. только после успешной записи делает новую board authoritative;
11. создаёт PGN projection или обновляет export;
12. публикует `MoveCommitted` event в analysis queue/UI.

Если запись не удалась, authoritative board остаётся старой. Повтор события использует idempotency key, чтобы не добавить второй одинаковый ход.

## 8. PGN/FEN и история

- FEN до/после каждого хода — для восстановления и проверки.
- UCI — канонический машинный ход.
- SAN — человекочитаемая нотация.
- PGN — итоговый экспорт партии с headers.
- Внутренний журнал событий — более богатый формат, чем PGN, потому что PGN не хранит evidence, confidence, correction history и timestamps.

PGN можно пересобрать из последовательности `MoveEvent`; журнал должен быть источником истины для расширенных данных.

## 9. Аналитический контур Stockfish

Stockfish запускается отдельным worker/процессом через UCI после `MoveCommitted`.

Для хода `m_t` можно анализировать позицию до и после хода:

1. Получить `fen_before`, `fen_after`.
2. Запустить engine analysis на обеих позициях с фиксированными limits (depth или time limit).
3. Привести оценки к перспективе одного игрока, который сделал ход.
4. Вычислить потерю оценки с правильным знаком.
5. Сохранить best move/PV/score/depth/time и эвристическую классификацию.

### 9.1. Почему Stockfish не определяет физический ход

Шахматный движок оценивает стратегическую силу и legal continuations. Если камера ошибочно распознала `e2e4` вместо `d2d4`, анализ движка может дать осмысленную оценку неверной позиции. Поэтому engine не является visual error corrector и не должен выбирать между физическими кандидатами на основании «лучшего шахматного хода».

### 9.2. Очередь и отказоустойчивость

- отдельный процесс Stockfish;
- bounded queue;
- timeout на каждую задачу;
- уникальный event_id;
- сохранение engine version/options;
- analysis result не редактирует MoveEvent и FEN;
- при недоступности engine регистрация продолжается;
- повторная задача не должна создавать дублирующий analysis result.

## 10. База знаний и формальные правила

На первой версии не требуется разворачивать отдельный Prolog/OWL/RDF сервер. Логико-символьный слой может быть реализован как:

- формальная шахматная модель `python-chess`;
- собственные правила принятия решения (thresholds, margin, occlusion, temporal requirements);
- доменные инварианты/проверки согласованности;
- объяснимые reason codes.

Отдельная онтология оправдана только если появится реальная задача управлять знаниями динамически, расширять доменную терминологию или выполнять сложные запросы по знаниям. Иначе она добавит сложность без улучшения move recognition.

## 11. Диагностические reason codes

Минимальный набор:

- `BOARD_NOT_FOUND`
- `GEOMETRY_UNSTABLE`
- `ORIENTATION_UNKNOWN`
- `HAND_OCCLUSION`
- `MOTION_ACTIVE`
- `OBSERVATION_INSUFFICIENT`
- `NO_LEGAL_CANDIDATE`
- `TOP_CANDIDATES_TOO_CLOSE`
- `LOW_ABSOLUTE_SCORE`
- `SOURCE_LOST`
- `ENGINE_UNAVAILABLE`
- `PERSISTENCE_FAILED`
- `OPERATOR_CONFIRMED`
- `OPERATOR_CORRECTED`
