## 1. Почему текущий подход «яркость/тень + эвристические пороги» несостоятелен

Эксперименты на реальных сессиях (`session_20261127_201713_aa6307`, `session_20261127_203135_03a951`, 23-минутный матч `2026-11-25 22-05-47.mp4`) и покадровый анализ вскрыли фундаментальные ограничения:

1. **Маскировка по яркости («полупрозрачное белое на белом» / «чёрное на чёрном»):**
   - При ходе `e2 -> e4` на реальной доске белая матовая пластиковая пешка на светлой клетке `e4` меняет среднее RGB-значение в центре клетки с `225.5` до `224.6` ($\Delta I_{\text{mean}} \approx 0.9$ градации).
   - Уход той же пешки со светлой `e2` даёт `delta = 0.017`, что ниже шумового порога фона на других клетках.
   - Дополнительно `np.sqrt` гамма-коррекция в `occupancy_tracker.py` сжимает светлый диапазон (`200 vs 230` $\to$ `225.8 vs 242.1`, теряя половину контраста).
2. **Ненадёжность теней и побочных эффектов наклона:**
   - Тень фигуры не инвариантна: при верхнем освещении или другом положении лампы тени может не быть вообще, либо она уходит на соседние клетки / за границу кадра.
   - Из-за перспективного наклона камеры верхняя часть фигуры на `e4` проецируется в соседнюю клетку `f4` (`diff_core = 62.8`). Предобученный `chesscog` (`InceptionV3` + `ResNet`, обученный на синтетических непрозрачных рендерах после warp нарезанных клеток) воспринимает нависание на `f4` как стоящую там фигуру, а саму `e4` считает пустой.
3. **Уязвимость «прямой подгонки углов» по линиям Хафа:**
   - На реальных кадрах линия границы доски (`h8-h1`) периодически смещается на внутреннюю границу горизонтали `g`/`h` или половину доски из-за текстур стола, фигур на краях и отсутствия семантического понимания углов доски (`a1/h1/a8/h8`).
4. **Искажённая передача данных между слоями («сломанный телефон»):**
   - `BoardOccupancyTracker` пытается «перевести» свои физические оценки обратно в 13-классовые вероятности (`cell_obs`), затем `MoveScorer` и `LegalMoveCandidateGenerator` интерпретируют эти вероятности через `predicted_piece` — по дороге теряя информацию и штрафуя друг друга.

## 4. Комплексная концепция переработки (без костылей по яркости)

Рекомендуется перестроить систему как **трёхслойную воронку с честным разделением ответственности** и устранением всех багов аудита:

### Слой 1. Надёжный фундамент, углы и движение
1. **Стабильная локализация углов (`a1/h1/a8/h8`):**
   - Исправить `corner_refinement.py` (запрет захвата неполной сетки/половины доски, взвешенный по длине `fitLine`, обязательная проверка шахматной каймы) И опционально поддержать **YOLO11-pose модель углов** (по аналогии с `surawut/chess-move-tracking-yolo11`), чтобы жёлтая рамка больше не смещалась на внутренние ряды.
   - На фронтенде привязать `#cornersCanvas` строго к реальному прямоугольнику отрисовки видео (с учётом `object-fit: contain`), а также остановить холостое считывание файлов/синтетики в режиме паузы.
2. **Честный детектор руки и движения:**
   - Починить ориентацию масок рук в `hand_detector.py` (`WHITE_RIGHT` / `BLACK_BOTTOM` / `WHITE_LEFT`), убрать ложную детекцию дерева как кожи.
   - В `MotionDetector`: добавить сравнение с **замороженным `baseline`-кадром** через многонаправленный градиент $\|\nabla I\|$, чтобы замершая рука не исчезала и плавные малоконтрастные ходы надёжно переводили FSM в `MOVING`.

### Слой 2. Беспривязочная (Non-Brightness) оценка позиции и ходов на основе всей доски
1. **Калибровка строго раздельных зон (`base` vs `lean_vector`) на старте партии:**
   - **Зона контакта базы:** центральная маска без пересечения с нижней полосой нависания, с вычитанием локального `lean_vector(file, rank)` (оценивается из геометрии камеры / известных фигур начальной расстановки, в т.ч. диагонально у краёв).
   - **Признаки без яркости и теней:**
     - **Структурный индекс сходства (SSIM-structure + градиентная энергия $\sqrt{I_x^2 + I_y^2}$)** без `np.sqrt`-сжатия светлых тонов и без сломанного `Sobel(1, 1)`;
     - **Реальные нейросетевые модели вместо (или поверх) синтетики `chesscog`:** интеграция предобученной модели на реальных фотографиях — в приоритете:
       - Вариант A (holistic board): **`ChessQueries` (`chessq-lite` / `ViT-S`) ONNX** на ключевых кадрах `VERIFYING` (сразу учитывает 3D-контекст и угол камеры);
       - Вариант B (unwarped base projection): **YOLO (`NAKSTStudio/yolov8m` / `yolo11n`) ONNX** по *неискажённому* кадру с проекцией точки основания $(x_{\text{base}}, y_{\text{base}})$ через гомографию $H$;
       - **Плюс** проверка на реальных видеороликах, имеет ли смысл добавлять `DINOv2`/глубину для полупрозрачных фигур (эмпирический тест на ваших кадрах `e4`/`f4` и 23-мин видео).
2. **Прямой Whole-Board Legal-Move Evaluator (удаление «сломанного телефона»):**
   - Вместо перезаписи `cell_obs` искусственными вероятностями и повторного пересчёта через `MoveScorer`/`detect_changed_squares`:
     - каждый легальный ход $m \in \text{legal\_moves}$ оценивается напрямую по: (1) очищению базы `from_sq` (структурное совпадение с эталоном пустой клетки + уход по `lean_vector`), (2) появлению структуры/фигуры в `to_sq` (база + детекция на базе/по `lean_vector`), (3) **глобальной тишине остальных ~60 клеток** (вето при постороннем изменении, автофокусе или перекрытии).
   - Убираем все противоречия `is_occupied=True / predicted_piece="empty"`, загрязнение `_last_cell_obs` и обход `DecisionGate` в 2-ply.

### Слой 3. Целостность FSM, Web UI и журнала событий
- Починить `NameError` (`frame.timestamp`), `SETTLING` при `timestamp == 0.0`, порядок калибровки ориентации после `MotionDetector`, двойной `rollback_move()`.
- Перенести `orchestrator._lock` на все чтения Web API / WS; добавить `WebSocketManager` thread-safe блокировки; исправить `events.jsonl` при `rollback`/`reset` (сохранение валидной хеш-цепочки или append-only compensation event / snapshot-логика, согласованная с `audit` и `RecoveryManager`).
