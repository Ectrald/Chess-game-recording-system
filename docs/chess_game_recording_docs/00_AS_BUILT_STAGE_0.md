# 00. Фактическое состояние реализации — ветка `STAGE/0`

## 1. Снимок репозитория

Проверенная ветка: `STAGE/0` (именно с косой чертой), commit `99d1bc9b1081e0d04765d5fe02f51615555581bc`. Это существенно: состояние `main` не следует использовать как единственный источник истины о текущей реализации.

Ветка содержит первый инфраструктурный вертикальный срез: типизированные контракты, конфигурацию, источники кадров, синтетический генератор, benchmark и автоматические тесты. Поэтому последующие этапы должны расширять существующие интерфейсы, а не заново создавать их.

## 3. Точные интерфейсы, от которых следует продолжать

### 3.1. `BaseVideoAdapter`

В `src/vision/video_adapter.py` определён абстрактный интерфейс:

```python
read() -> Optional[Frame]
get_fps() -> float
get_frame_count() -> int
seek(frame_id: int) -> bool
is_opened() -> bool
release() -> None
```

Реализации:

- `OpenCVVideoAdapter` — файл, камера, RTSP через `cv2.VideoCapture`;
- `SyntheticVideoAdapter` — выдаёт кадры из `SyntheticBoardGenerator`;
- `create_video_adapter(config)` — фабрика по `CameraConfig.source_type`.

**Контракт, который надо сохранить:** алгоритмы распознавания не должны знать, откуда пришёл кадр. При этом текущий `None` неоднозначен: это может быть EOF, временный сбой чтения или потеря RTSP-соединения. До реализации live-stream recovery нужно ввести явное состояние источника или различить `FrameAvailable`, `EndOfStream`, `TemporaryReadFailure` и `SourceLost`.

### 3.2. `Frame`

Текущие поля: `frame_id`, `timestamp`, `image`, `width`, `height`. Валидатор проверяет `np.ndarray` и `ndim` 2/3; размеры могут выводиться из `image.shape`.

**Нужно усилить:** задать единый цветовой порядок (рекомендация — BGR внутри OpenCV-контура, RGB только на границе ML-модели), dtype `uint8` для типичного видеокадра, допустимые каналы 1/3/4, непрерывность/обработку копии и согласованность width/height с формой массива. Timestamp должен быть монотонной временной меткой источника, а не всегда вычисляться как `frame_id / fps`.

### 3.3. `BoardGeometry`

Текущие поля: четыре угла `TL, TR, BR, BL`, optional homography 3×3, `confidence`, `is_valid`, `orientation_calibrated`.

Текущая проверка матрицы гарантирует только форму 3×3. Она не проверяет конечность чисел, выпуклость и порядок вершин, самопересечение четырёхугольника, площадь, обусловленность матрицы и reprojection error.

**Нужно усилить:** разделить `detected_corners` в координатах исходного кадра, `H_image_to_board`, `H_board_to_image`, `reprojection_error`, `geometry_quality`, `orientation` из enum `{UNKNOWN, WHITE_BOTTOM, BLACK_BOTTOM}` и `calibration_status`. Не использовать один `confidence` как одновременно уверенность детектора и физическое качество геометрии.

### 3.4. `CellObservation`

Текущая модель хранит словарь вероятностей, предсказанную фигуру, confidence, occupancy и `is_occluded`.

Проблемы текущего контракта:

1. Валидатор ограничивает каждую вероятность интервалом [0, 1], но не проверяет наличие всех 13 классов и сумму вероятностей.
2. Можно передать пустой или неполный словарь, в котором максимум не имеет смысла.
3. Поле `confidence` может противоречить `predicted_piece` и распределению.
4. `is_occupied` может противоречить вероятности `empty`.
5. Boolean `is_occluded` не описывает долю перекрытия и источник маски.

**Рекомендация:** хранить полное `probabilities: dict[PieceClass, float]` с ключами строго по каноническому алфавиту. Если inference выдаёт logits, преобразование в normalized probabilities делать ровно один раз в адаптере модели. Отдельно хранить `occlusion_ratio`, `occlusion_source` и `is_reliable`.

### 3.5. `BoardObservation`

Текущая модель требует ровно 64 ключа `a1`…`h8`. Это полезный инвариант. Но не проверяется, что `cells[key].square == key`.

Метод `diff_squares(other, threshold=0.5)` сейчас сравнивает бинарную занятость и `predicted_piece`; параметр `threshold` фактически не применяется. Его нужно либо удалить, либо реализовать вероятностную дистанцию.

**Рекомендация:** сравнивать распределения вероятностей по клеткам, игнорируя клетки с occlusion или плохой геометрией. `changed_squares` должен быть результатом отдельной функции с явно заданным критерием, а не побочным эффектом `argmax`.

### 3.6. `MoveHypothesis` и `MoveEvent`

`MoveHypothesis` содержит UCI/SAN, затронутые клетки и несколько баллов. В следующей версии следует добавить `candidate_id`, `fen_before`, список evidence frame IDs, `score_components`, `accepted/rejected_reason`, а score-компоненты привести к согласованной шкале.

`MoveEvent` уже содержит полезные поля: номер полухода, FEN до/после, UCI/SAN, confidence, timestamp, evidence frame id, optional engine evaluation и blunder flag. Текущая проверка FEN структурная (6 полей и 8 рангов), но не гарантирует полный валидный FEN и легальность перехода.

**Критический принцип:** `MoveEvent` создаётся только после `python-chess`-проверки legal move и атомарной фиксации события. Оценка движка не должна участвовать в определении того, какой ход был физически сделан.

## 4. Конфигурация и зависимости

`configs/default_config.yaml` уже отражает параметры vision, temporal, decision, analysis и camera. Pydantic-конфигурация проверяет диапазоны ряда параметров и сумму весов `DecisionConfig`.

Фактический `requirements.txt` пока содержит только базовые зависимости: NumPy, Pydantic, PyYAML, python-chess, OpenCV, Pillow, pytest. В нём нет PyTorch/torchvision, MediaPipe, Ultralytics, MLflow, ONNX Runtime, GUI framework или интеграции Stockfish. Поэтому эти компоненты нельзя считать установленными или рабочими только на основании README/ROADMAP.

Рекомендация: добавлять зависимость в `requirements` только на этапе, когда соответствующий модуль входит в разработку. Для training окружения и runtime окружения использовать отдельные dependency groups/файлы, чтобы не тянуть PyTorch и training stack в простой CPU runtime.

## 5. Существенное ограничение синтетического генератора

`SyntheticBoardGenerator` строит доску на основе `python-chess`, отображает поля и фигуры в виде контрастных круглых маркеров с буквами `P/N/B/R/Q/K`, применяет гомографию к плоскости доски, моделирует перемещение условного маркера и полупрозрачную эллиптическую руку/тень.

Это полезно для:

- проверки формата `Frame`;
- тестов синхронизации и временных меток;
- воспроизводимого тестирования геометрии на известной гомографии;
- проверки логики FSM/решателя после их появления;
- тестов специальных ходов и benchmark;
- fault injection (шум, искусственная окклюзия).

Это **не является реалистичным датасетом для обучения распознаванию физических шахматных фигур**. Модель, обученная только на таких значках, будет учить значки, а не форму разных деревянных/пластиковых наборов. Для обучения нужны реальные фотографии клеток и/или фотореалистичные 3D-рендеры с реальными силуэтами фигур и доменным разрывом, измеряемым на реальных комплектах.

## 6. Найденные ограничения benchmark

Текущая `compute_fen_distance` сравнивает только размещение фигур на 64 клетках. Она не учитывает сторону хода, права рокировки, поле en-passant, счётчик полуходов и номер полного хода. Это не полная дистанция FEN.

`BenchmarkEvaluator.evaluate` сравнивает до `min(predicted, ground_truth)` ходов. Лишние предсказанные ходы после окончания эталона не превращаются в ошибку. Отсутствующие ходы обрабатываются лучше, чем лишние. Время задержки вычисляется как `max(0, predicted.timestamp - ground_truth_timestamp)`, поэтому отрицательное смещение не сигнализирует об ошибке синхронизации.

**Рекомендация:** оставить `piece_placement_distance` как одну метрику, а проверку полной позиции выполнять через `chess.Board.fen()`/свойства объекта. В benchmark включить FP/FN по событиям ходов, ложные подтверждения, пропущенные ходы, лишние ходы, долю `UNCERTAIN`, ручные вмешательства и полный game exact match.

## 7. Границы доверия к документам текущей ветки

`README.md`, `ROADMAP.md` и `06_DATA_AND_MLOPS.md` (ранее `MLOPS_AND_DATASETS.md`) описывают будущие компоненты и целевые показатели. Они полезны как проектные источники, но не доказывают наличие соответствующего кода или фактически достигнутую производительность. Особенно не следует трактовать `EfficientNet-B0`, YOLO, MediaPipe, Stockfish, MLflow и ONNX как реализованные компоненты Stage 0.

## 8. Результат аудита Stage 0

Stage 0 уже создал хороший фундамент: данные имеют каноническую шахматную семантику, source video отделён интерфейсом, тестовая партия воспроизводима, конфигурация централизована, а baseline benchmark существует. Следующий инженерный шаг — усилить точность контрактов и семантику ошибок источника, затем реализовать геометрию доски. Не следует пересоздавать структуры с нуля или обучать piece classifier до получения корректных real-world crops.
